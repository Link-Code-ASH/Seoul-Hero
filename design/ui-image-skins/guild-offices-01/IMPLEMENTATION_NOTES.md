# 런타임 연결 메모

2026-10-05 사용자 승인 후 아래 내용을 현재 워크트리에 구현했다. 라이브 UI는 HeroGuildOfficeScreen, 표시 모듈은 HeroGuildOfficeWorld이며 기존 Profile.guild_action을 재사용한다. 원본 콘텐츠를 exporter로 갱신했고 v3 이관의 메모리 검증 31개를 확인했다. 본 폴더와 실제 사용자 저장은 검증 중 건드리지 않았다. 아래에는 구현 기준을 보존한다.

## 층 데이터와 공용 계산

- 원본 `src/data/guildManagement.ts`의 balance에 `roomsPerFloor: 3`, `floorUnlockOfficeLevels: [1, 2, 3]`를 추가한다. 기존 4/8칸 기준의 `initialRoomSlots`, `expandedRoomSlots`, `expandedOfficeLevel`은 새 계산에서 사용하지 않는다. 운영실 효과 문구도 Lv.2 2층·Lv.3 3층으로 맞춘 뒤 기존 exporter로 가져온다.
- 길드 상태에 정수 `unlockedFloors`를 추가한다. 새 길드는 1이며, 이후에는 감소하지 않는다. 층 목록은 데이터 배열 길이에서 얻고 미래 층은 배열에 순서대로 추가한다. 슬롯 0 운영실과 기존 시설/공사 슬롯 ID를 유지한다.
- 계산은 `HeroGuildState`에 모은다: `eligible_floors(data, office_level)`, `floors(data, guild)`, `room_count(data, guild)`, `sync_unlocked_floors(data, guild) -> bool`. 유효 층 수는 저장값과 현재 운영실의 해금 가능 층 중 큰 값, 방 수는 층 수 × roomsPerFloor다. sync는 값을 늘린 경우만 true를 반환한다.
- `HeroGuildRules.rooms`는 공용 room_count를 사용한다. 건설·이동, 방 목록, 이동 선택 목록, 표시 모듈도 같은 결과를 사용한다. 8종 시설의 중복 건설은 계속 금지하므로 슬롯 8은 추가 빈 공간이다.

## v2 → v3 저장 이관

- Profile 형식만 2에서 3으로 올린다. 전투 체크포인트 형식, `sourceSaveVersion`, `Profile.guild_action` 인터페이스는 바꾸지 않는다.
- v2 입력은 **기존 검증 기준으로 먼저** 검사한다. 기존 용량은 운영실 Lv.3 미만 4, 이상 8이며 슬롯 최대값은 7이다. 신규 3/6/9 기준으로 v2를 먼저 검증하면 유효한 슬롯 3·6·7과 진행 중 공사를 거부한다.
- 기존 검증 본문을 공용 내부 함수로 유지하고 `valid_legacy_v2`만 옛 용량을 전달하는 방식으로 검증 중복을 줄인다. 신규 valid는 층 필드의 정수 범위와 데이터 기준 최대 슬롯을 검사한다. 시설뿐 아니라 construction job.slot도 같은 용량으로 검사한다.
- 유효한 v2 길드를 깊은 복사한 뒤 `unlockedFloors = max(ceil(old_capacity / 3.0), eligible_floors(...))`만 추가한다. 운영실 Lv.1~2 저장은 최소 2층, Lv.3 이상은 3층이다. 지어진 방의 개수 대신 **기존 열린 용량**을 사용해야 빈 공간도 다시 잠기지 않는다. 시설·직원·재화·연구·작업 시각·공사 예약·nextJobId 등 기존 필드는 그대로 둔다.
- 기존 v1의 구형 길드 교체 동작은 유지하되 새 create로 만든 1층 상태를 그대로 v3으로 올린다. v1에서 새 길드를 만든 다음 v2 grandfather 계산을 적용하면 불필요한 2층이 열린다.
- `_migrate`의 while에는 현재 version 1 분기만 있다. 형식 상수만 3으로 올리면 version 2에서 무한 반복한다. 모든 지원 버전이 명시적으로 진행되도록 변경한다.
- 미래 형식의 본 저장·백업·전투 체크포인트에서 writable=false가 되는 기존 보호, atomic 임시 저장, 백업 회전/복구, import_backup의 공용 이관 경로를 유지한다. 실제 사용자 저장 파일을 시안이나 검증에 읽거나 쓰지 않는다.

## 시계와 표시 책임

- 운영실 construction 완료에서 해금 층을 즉시 동기화한다. advance의 같은 시각/시간 역행 조기 반환 경로에서도 필요한 층 동기화 결과를 놓치지 않는다. 층 증가는 생산량·작업 완료 시각을 바꾸지 않는다.
- valid는 저장 층 수가 운영실의 최신 해금 수보다 작은 것만으로 거부하지 않는다. 현재 콘텐츠에 미래 층이 추가되었을 때도 기존 v3 저장을 읽고 sync로 새 해금을 반영할 수 있어야 한다.
- 직원 노드는 ID로 유지하고 목적지만 갱신한다. 직원 위치·사무실 선택·건물 스크롤은 UI 실행 상태이며 영구 저장에 넣지 않는다. 기존 atlas의 4열은 Lv.1/4/7/10 원화 단계이므로 화면의 층당 3칸과 혼동해 crop을 3열로 바꾸지 않는다.

## 필요한 좁은 확인

승인 후 메모리상의 새 상태, v1 교체, v2 운영실 Lv.1 슬롯 3/공사, v2 운영실 Lv.3 슬롯 7/공사, v3 슬롯 8, 손상된 v2, 미래 버전 보호를 확인한다. 이관 후 기존 필드와 작업 시각의 보존도 비교한다. Godot 가져오기·스크립트 로드·저장 없는 캡처만 추가하며 전체 테스트·자동 플레이 QA는 하지 않는다.

## 고정 관리 패널 수정 방향

- 915×412에서 건물(12,65,547,335)과 패널(573,65,330,335)을 항상 확보한다. 패널 개폐 때 world 폭/배율/스크롤을 바꾸지 않는다. 오른쪽 비선택 상태는 입력 차단되는 빈 배경이다.
- 하단 단축키 버튼4개를 제거한다. 왼쪽 입력은 사무실 선택과 층 스크롤뿐이며 모든 명령·대상 선택은 오른쪽에서 수행한다.
- 건설된 시설은 제목/레벨/닫기와 관리·직원·작업 탭을 고정한다. 탭마다 내용만 내부 스크롤하고 선택시설ID/탭/스크롤은 실행 중 UI 상태에만 둔다. 빈방/잠긴층/신규공사는 별도 건설·조건·공사 상세다.
- 운영실 직원/작업 탭은 전체 목록, 다른 시설은 해당 시설 목록이다. 운영실 관리에 claim과 deploy를 넣어 초반부터 접근하게 한다. claim은 생산 외 탐험·제조 pendingRewards까지 수령하는 기존 명령이다.
- 기존 _facility/_staff/_hire/_jobs/_expedition/_workshop와 command/deploy를 재사용하되 시설 컨텍스트/필터를 추가한다. 시설 이동은 기존 교환 규칙을 유지하고 오른쪽 대상 목록으로 선택한다. 이동 후 선택시설ID를 추적해 패널이 따라간다.
- 직원·작업의 세부 페이지와 다시 돌아오는 경로도 같은 시설 컨텍스트를 유지한다. 새 사무실 선택은 기존 시설의 탭/스크롤을 저장한다. 공사 완료나 UI 갱신은 직원 노드를 재생성하지 않는다.
